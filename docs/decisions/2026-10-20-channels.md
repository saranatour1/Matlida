# Channels: email, messaging and calls

The decision trail for the channels stack, one PR at a time. Each entry says
what was decided, what else was considered, the evidence, and what was parked.

## Context

Matilda already texts over iMessage, Telegram and WhatsApp through Photon,
calls you in the app, and sends auth emails through Resend. The stack adds a
Connections page, a personal email address per user, inbound email answered
by an assistant, email reminders, hardening of inbound texting, and a setup
guide. Nobody was awake to answer questions while it was built, so each
decision below was made on the evidence listed and can be reversed in review.

## PR 1: Connections page

### One registry, one query

- Decision: every channel is an entry in `CHANNELS` (`convex/lib/channels.ts`),
  a discriminated union on `via`: `photon` (an app linked through Photon),
  `email`, `tool` (always on through the AI gateway) and `planned`. Statuses
  come from one pure function, `channelStatus`, fed by one authed query,
  `channels.list`, which reads existing data: phone links, the mailbox (from
  PR 2), and which env vars are set.
- Alternatives: keep the hardcoded list in the details panel and add another
  on the new page (two sources of truth); a `channels` table (nothing to
  store, every fact already lives elsewhere).
- Evidence: before this PR the app names lived in `lib/models.ts` and the
  details panel kept its own hardcoded list of connectors. The registry
  replaces both, and the Messaging page reads the names from it.
- The query reports env vars as present or missing by name only. The browser
  never receives a value, and a test asserts the JSON has none.

### Where the code lives

- Decision: `convex/models/channels/functions.ts` holds the query even though
  there is no `channels` table, because the project convention is one
  `<name>Api` per `convex/api/<name>.ts`, and the alternative, hiding the query
  in `texts`, would bury the single source of truth. The registry itself is in
  `convex/lib/` so the browser can import it like `lib/models.ts`.
- Parked: a `channels` table. Nothing needs persisting.

### Messaging page stays, Connections links to it

- Decision: Connections is the overview and the linking flow stays on
  Messaging, which Connections and the panel link to. Both pages read the
  registry; Settings and the command menu only link to Connections.
- Alternative: fold Messaging into Connections. Rejected for this PR to keep
  the diff small and the `link <code>` flow unchanged; it can move later with
  no change to the registry.

### SMS rides on the iMessage line

- Decision: there is no separate SMS channel. Photon's iMessage platform page
  says lines reach SMS and RCS phones ("When iMessage isn't available, Photon
  automatically falls back to SMS or RCS", photon.codes/platform/imessage) and
  the SDK exposes `sender.service` as `iMessage | SMS | RCS`. The iMessage
  entry says so in its description.
- Alternative: an SMS entry marked coming soon. Wrong, since it works today.

### Phone calls are coming soon

- Decision: `phone` is a `planned` entry with the reason. Photon voice is SIP
  only, with no call control from a Convex action. The design note is in the
  setup guide (PR 5).

### Branches

- Decision: the stack uses the session's designated branch for PR 1 and the
  same name with `-2` to `-5` for the rest, so every branch keeps the prefix
  the operator gave the session.

### Noticed, not changed

- This environment's `CONVEX_DEPLOYMENT` points at the shared dev
  deployment that must not be touched, and no agent deploy key was
  present. Nothing in this stack was run against a deployment: verification
  is unit tests, typecheck, lint and the production build. `convex codegen`
  was run with the deployment variables unset; it does not contact a
  deployment.
- PRs #46 and #47 were already closed when the stack started (#47 is merged
  into master), so there was nothing to avoid.

## PR 2: A personal email address per user

### One mailbox per user, answered by one workspace

- Decision: a `mailboxes` table with one row per user: the handle and the
  workspace (`projectId`) whose assistants answer it. Claiming from another
  workspace's Connections page moves the address there; the other workspace
  then shows it as ready with "answers in another workspace".
- Alternatives: a handle column on `users` (no new table, but the answering
  workspace and, in PR 3, the per-assistant threads need a home); one mailbox
  per workspace (the task asks for one per user).
- Evidence: the task: "a personal email address per user (users, not bots)",
  and Connections is per workspace, so the status has to say where the
  address answers.

### Handle rules

- Decision: `parseHandle` in `convex/lib/handles.ts` trims, lowercases and
  checks `[a-z0-9._-]{3,32}`, refuses a leading, trailing or doubled dot (so
  every handle is a plain RFC 5321 local part), and refuses the reserved
  list: RFC 2142 names, admin names, automated senders, mail-operations
  names, account words and `matilda`. The same rules run as a Zod transform
  (`zHandle`) on the mutation, so the form gets the reason as the error.
- Uniqueness: `by_handle` index checked in the mutation. Convex serializes
  conflicting mutations, so two claims of the same handle can't both commit.
- Evidence: RFC 2142 for the role names; the dot rule avoids addresses that
  would need quoting and that some receivers reject.

### Only the verified sign-in email

- Decision: claiming requires `users.email`, which the app only sets from a
  verified address (`syncProfile`). The address is shown next to the handle
  with "Replies go only there". PR 3 enforces it on inbound mail.

### Parked

- Renaming keeps the mailbox row; releasing deletes it, which frees the
  handle for anyone. A cool-down before a released handle can be reclaimed
  by another user would stop old mail reaching a new owner. Parked: Resend
  drops mail for unknown handles anyway, and the owner check in PR 3 means
  a new owner's assistants never see the old owner's mail.

## PR 3: Inbound email answered by an assistant

### Sender authentication: Resend's results, and fail closed

- Decision: an email is accepted only when all of these hold: it's to a
  claimed handle at `MAIL_DOMAIN`; its bare From address equals the mailbox
  owner's verified sign-in email; and Resend's receiving API reports
  `authentication.dmarc === 'pass'` and `authentication.dkim === 'pass'`.
  Anything else is rejected with a short reason code and gets no reply, so
  there is no backscatter.
- Evidence: Resend's retrieve-received-email reference says the
  `authentication` object holds "the SPF, DKIM, and DMARC results computed
  when the email was received. These come from the receiving mail server,
  not from the message headers, so the sender cannot forge them", and that
  `dkim` is `gray` when "the message is not signed, or the signing domain
  does not match the From domain", so `pass` is an aligned DKIM pass. That
  is exactly the receiving side's Authentication-Results the task asked
  for first.
- Alternatives: verifying DKIM and DMARC ourselves over the raw message with
  `mailauth` in a Node action. Parked: it adds a large dependency tree and a
  download of the raw message, for a result Resend already computes. Older
  emails where `authentication` is `null` are refused (`no_auth_results`).

### Webhook: Svix verification without a new dependency

- Decision: `convex/lib/svix.ts` verifies `svix-id`, `svix-timestamp` and
  `svix-signature` with Web Crypto over the raw bytes, with the standard
  5-minute tolerance, before the body is parsed. Missing headers are a 400,
  a bad or stale signature a 401, and a missing `RESEND_WEBHOOK_SECRET` a
  500, so nothing is ever processed unsigned.
- Alternatives: the `svix` package or `resend.webhooks.verify` (the Resend
  component already depends on both, but only as transitive packages, and
  the component's own handler accepts only sending events). The algorithm
  is 30 lines and tested, including a signing helper used by the tests.

### Replays

- Decision: two dedupe keys, both indexed on `inboundEmails`: Resend's
  `email_id` (retries keep it) and the RFC `Message-ID` (a redelivery
  under a new id, or the same message to two of our addresses). The webhook
  acknowledges a duplicate with 200 and starts nothing. The reply itself is
  sent with `idempotencyKey: inbound:<email_id>`, so a retried send step
  can't send twice.

### The pipeline on `@convex-dev/workflow`

- Decision: `answerEmail` runs fetch (facts only), verify, reply, send as
  steps, with `record` as the `onComplete` handler that marks a workflow
  that ended without a reply. Actions retry (3 attempts by default; the
  model reply 2), mutations are exactly-once. The body is fetched only in
  the reply step, after verification, so a rejected email's text never
  enters our database or the workflow journal.
- Alternatives: `ctx.scheduler.runAfter` chains (no retries or history), or
  doing everything in the webhook (the isolate is frozen after the 200).

### Routing and threads

- Decision: `@name` at the start of the subject (after any Re:/Fwd:) or of
  the first line picks the assistant, and sticks (`activeBotId` on the
  mailbox), exactly like texting. The router is now the shared
  `convex/lib/addressee.ts`, used by texting too. One thread per mailbox
  and assistant, titled "Ivy · Email", so the exchange shows in the app.
  An unknown name gets a short list of who can be emailed, from the lead.

### Untrusted content

- Decision: only the plain-text part is read, with quoted history, "On …
  wrote:" lines, signatures and forwarded headers cut, capped at 20,000
  characters. HTML-only mail gets a fixed one-line reply. Attachments are
  never fetched. The reply's recipient is the mailbox owner's email read
  from the database inside the send step, never anything from the message,
  and the tests assert that every send went to the owner.
- Rate limit: `@convex-dev/rate-limiter`, token bucket per owner, a burst
  of 5 then 20 an hour, checked after authentication so a stranger can't
  spend it. A limited email is recorded `rate_limited` with no reply.

### Reply style

- Decision: a new `via: 'email'` style for the lead and bots: plain text,
  short paragraphs, no greeting or sign-off. From is the assistant's name at
  the owner's handle; the subject is `Re: <original>`, and In-Reply-To and
  References thread it under the owner's email.

### Noticed

- `pnpm check` runs `tsc` before `vite build`, so a new route file fails
  the first typecheck until the build has regenerated
  `src/routeTree.gen.ts`. Running `vite build` once first fixes it.
- Draining the workflow in tests with `finishAllScheduledFunctions` moves
  fake time by the workpool's minute-long monitor timers, so a rate limit
  test can't go through the whole pipeline; the limit is tested at the
  verify step where it applies.

### PR 3, after review

An adversarial review of the inbound pipeline found these, all fixed in the
same PR:

- DMARC: Resend reports `dmarc: 'gray'`, not `pass`, when "SPF or DKIM
  passed but the sending domain has no DMARC policy or uses p=none", and
  Gmail publishes `p=none`. The gate now requires `dkim: 'pass'` (an
  aligned DKIM pass by Resend's definition) with DMARC `pass` or `gray`,
  and still refuses `fail`, `processing_failed`, `unknown` and missing
  results. Without this, most real owners would have been rejected.
- Auto-responders: an out-of-office at the owner's address would answer
  our reply, which we would answer again. Mail marked `Auto-Submitted`
  (other than `no`), `X-Auto-Response-Suppress`, `X-Autoreply` or a bulk
  `Precedence` is rejected as `auto_submitted`, and our replies carry
  `Auto-Submitted: auto-replied` so the other side stays quiet (RFC 3834).
- Recipients: an email to two users' assistants was handled for the first
  handle found, so the sender's own assistant could reject it. The sender's
  own mailbox is now chosen among every To and Cc recipient at the domain.
- Routing: the subject's tag won over the first line's, so inside a thread
  whose subject still says `@Ivy` the owner couldn't switch. The first line
  now wins.
- Retries: the reply step runs at most once, so a retry can't bill the
  model twice or save the prompt twice; the fetch retries for about two
  minutes instead of seconds.
- Cost and spam: mail to a handle nobody claimed is dropped at the webhook,
  from the recipients in the event, before a row, a workflow or a fetch.
- Privacy: the workflow journal (addresses, the reply) is deleted when the
  workflow ends; a daily cron drops the Resend component's record of mail
  older than a week; the webhook's 500 no longer names the env var;
  Message-IDs are capped; the failure log is truncated.
- Tests cover each of these, including the verify-level duplicate branch.
