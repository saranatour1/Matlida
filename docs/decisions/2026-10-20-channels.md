# Channels: email, messaging and calls

The decision trail for the channels stack, one PR at a time. Each entry says
what was decided, what else was considered, the evidence, and what was parked.

## Context

Matilda already texts over iMessage, Telegram and WhatsApp through Photon,
calls you in the app, and sends auth emails through Resend. The stack adds a
Connections page, a personal email address per user, inbound email answered
by an assistant, email reminders, hardening of inbound texting, and a setup
guide. Nobody was awake to answer questions while it was built, so each
decision below was made on the evidence listed and can be reversed in review.

## PR 1: Connections page

### One registry, one query

- Decision: every channel is an entry in `CHANNELS` (`convex/lib/channels.ts`),
  a discriminated union on `via`: `photon` (an app linked through Photon),
  `email`, `tool` (always on through the AI gateway) and `planned`. Statuses
  come from one pure function, `channelStatus`, fed by one authed query,
  `channels.list`, which reads existing data: phone links, the mailbox (from
  PR 2), and which env vars are set.
- Alternatives: keep the hardcoded list in the details panel and add another
  on the new page (two sources of truth); a `channels` table (nothing to
  store, every fact already lives elsewhere).
- Evidence: before this PR the app names lived in `lib/models.ts` and the
  details panel kept its own hardcoded list of connectors. The registry
  replaces both, and the Messaging page reads the names from it.
- The query reports env vars as present or missing by name only. The browser
  never receives a value, and a test asserts the JSON has none.

### Where the code lives

- Decision: `convex/models/channels/functions.ts` holds the query even though
  there is no `channels` table, because the project convention is one
  `<name>Api` per `convex/api/<name>.ts`, and the alternative, hiding the query
  in `texts`, would bury the single source of truth. The registry itself is in
  `convex/lib/` so the browser can import it like `lib/models.ts`.
- Parked: a `channels` table. Nothing needs persisting.

### Messaging page stays, Connections links to it

- Decision: Connections is the overview and the linking flow stays on
  Messaging, which Connections and the panel link to. Both pages read the
  registry; Settings and the command menu only link to Connections.
- Alternative: fold Messaging into Connections. Rejected for this PR to keep
  the diff small and the `link <code>` flow unchanged; it can move later with
  no change to the registry.

### SMS rides on the iMessage line

- Decision: there is no separate SMS channel. Photon's iMessage platform page
  says lines reach SMS and RCS phones ("When iMessage isn't available, Photon
  automatically falls back to SMS or RCS", photon.codes/platform/imessage) and
  the SDK exposes `sender.service` as `iMessage | SMS | RCS`. The iMessage
  entry says so in its description.
- Alternative: an SMS entry marked coming soon. Wrong, since it works today.

### Phone calls are coming soon

- Decision: `phone` is a `planned` entry with the reason. Photon voice is SIP
  only, with no call control from a Convex action. The design note is in the
  setup guide (PR 5).

### Branches

- Decision: the stack uses the session's designated branch for PR 1 and the
  same name with `-2` to `-5` for the rest, so every branch keeps the prefix
  the operator gave the session.

### Noticed, not changed

- This environment's `CONVEX_DEPLOYMENT` points at the shared dev
  deployment that must not be touched, and no agent deploy key was
  present. Nothing in this stack was run against a deployment: verification
  is unit tests, typecheck, lint and the production build. `convex codegen`
  was run with the deployment variables unset; it does not contact a
  deployment.
- PRs #46 and #47 were already closed when the stack started (#47 is merged
  into master), so there was nothing to avoid.

## PR 2: A personal email address per user

### Email goes through Photon

- Decision: the assistants' mail is sent and received by Photon's Email channel
  (its beta platform API, `PHOTON_PROJECT_ID` and `PHOTON_API_KEY`), on a
  domain connected in Photon's dashboard.
- Why: the operator already uses Photon for messaging and has the domain
  connected there. Photon publishes the DNS records and accepts mail for any
  address on the domain, so claiming a handle needs no call to Photon.

### One mailbox per user, answered by one workspace

- Decision: a `mailboxes` table with one row per user: the handle and the
  workspace (`projectId`) whose assistants answer it. Claiming from another
  workspace's Connections page moves the address there; the other workspace
  then shows it as ready with "answers in another workspace".
- Alternatives: a handle column on `users` (no new table, but the answering
  workspace and, in PR 3, the per-assistant threads need a home); one mailbox
  per workspace (the task asks for one per user).
- Evidence: the task: "a personal email address per user (users, not bots)",
  and Connections is per workspace, so the status has to say where the
  address answers.

### Handle rules

- Decision: `parseHandle` in `convex/lib/handles.ts` trims, lowercases and
  checks `[a-z0-9._-]{3,32}`, refuses a leading, trailing or doubled dot (so
  every handle is a plain RFC 5321 local part), and refuses the reserved
  list: RFC 2142 names, admin names, automated senders, mail-operations
  names, account words and `matilda`. The same rules run as a Zod transform
  (`zHandle`) on the mutation, so the form gets the reason as the error.
- Uniqueness: `by_handle` index checked in the mutation. Convex serializes
  conflicting mutations, so two claims of the same handle can't both commit.
- Evidence: RFC 2142 for the role names; the dot rule avoids addresses that
  would need quoting and that some receivers reject.

### Only the verified sign-in email

- Decision: claiming requires `users.email`, which the app only sets from a
  verified address (`syncProfile`). The address is shown next to the handle
  with "Replies go only there". PR 3 enforces it on inbound mail.

### Parked

- Renaming keeps the mailbox row; releasing deletes it, which frees the
  handle for anyone. A cool-down before a released handle can be reclaimed
  by another user would stop old mail reaching a new owner. Parked: PR 3
  drops mail for unclaimed handles anyway, and the owner check in PR 3 means
  a new owner's assistants never see the old owner's mail.
